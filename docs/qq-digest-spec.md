# QQ 群聊晚报需求

状态：各项需求与 agent 架构已确认，TypeScript 版本已完成离线实现与测试；真实服务联调及用户验收待完成。

## 已确认

- 将项目直接重构为 TypeScript，使用 NapCat + pi SDK，不采用 Python 与 TypeScript 混合运行。先在当前 Windows 电脑验证。
- 指定群白名单，先从一个群验证；仅接收运行期间的新消息，不补取启动前或停机期间的聊天历史。
- 处理指定群所有成员发布的消息，再判断是否属于关注主题；主题暂定 agent 开发、产品。闲聊不收录。
- 打开消息中的链接，读取公开网页文字，用于主题判断及摘要。所有成员的纯链接消息也先读正文再判断。
- 不登录网页，不转录音视频。读取失败而群消息足以判断主题时，收录并标明正文未读取；纯链接无法判断的内容列入晚报末尾的“待读取链接”。
- 每天北京时间（Asia/Shanghai）20:00 出报，覆盖前一天 20:00 到当天 20:00；首次从开始接收时算起。
- 通过 Telegram bot 发送到用户与机器人的私聊。凭据通过本地环境配置，接收目标需配置 chat_id。
- 每条包含：主题摘要、关键原话、链接（没有则省略此行）、发言人、群、时间。关键原话来自群消息。
- 无内容时也发送“本期无符合条件的内容”。错过发送时间后恢复时补发最近一期，并标明记录缺口。

## 已确认的处理边界

- 产品主题包括 AI 产品发布与体验、产品设计、用户需求、商业化案例；排除普通购物推荐和广告。
- 只读取群消息直接分享的页面，不继续遍历页面内链接。同一期重复链接合并为一个条目，保留相关发言人与来源。
- 本地仅保存指定群范围内的消息；群消息及网页正文保留 7 天，生成的晚报最多保留一周。
- Telegram 发送失败自动重试并保存发送进度，长晚报分段发送。投递结果不明时优先保证送达，接受偶发重复，通过日期和分段编号识别。

## 第一版实现与验收

- 功能：接收消息、范围过滤、存储、公开网页读取、主题判定、晚报生成、定时投递与恢复。
- 必要知识：消息事件如何进入程序；群聊记录如何成为模型输入；定时窗口和发送状态如何独立保存。SDK API 和 TypeScript 语法可随用随查。
- 助手负责：主要实现、配置示例、自动化测试与操作说明。实际账号登录及私密配置在本地完成。
- 软件验收：覆盖范围过滤与闲聊排除、纯链接主题判断、网页读取失败、重复链接合并、20:00 窗口边界、空晚报、重启补发、分段与失败重试、7 天清理。模拟测试通过与真实服务联调通过分别记录。
- 用户验收：真实指定群的样例消息进入下一份 Telegram 晚报，格式和筛选符合预期；用户确认结果后才记录为用户验收通过。
- 暂缓：聊天历史补取、登录网页、音视频转录、网页递归抓取、管理界面、向量检索及多 agent 框架。QQ 群内 @ 对话已独立进入实现范围，见 [QQ 对话需求](qq-chat-spec.md)。
- 开发可按接收存储、筛选生成、定时投递三个可验证阶段推进；不要求一次三小时完成全项目。

## 技术事实与实现边界

- 用户提供的 SDK 文档：https://pi.dev/docs/latest/sdk 。本次核查显示 SDK 面向 Node.js / Bun，提供 TypeScript 接口。
- pi 用于模型相关处理；应用负责消息接收、存储、时间窗口和 Telegram 投递。实施时核实并固定依赖版本。
- 程序固定群号、QQ 号、时间窗、数据保存和投递边界；pi agent 自主查询本期消息、按需读取直接链接、筛选主题、合并内容并生成摘要。agent 无 Shell、写文件或任意 URL 读取能力，最终引用由程序校验。
- 软件验收与用户学习验收分别记录。离线类型检查、构建及自动化测试已通过；真实 NapCat、DeepSeek、Telegram 联调和用户验收尚未完成。

## 最新采集与保留规则（2026-09-24）

指定群所有成员的运行期间新消息都会采集，旧 QQ_AUTHOR_IDS 配置不再生效；仍不补取停机历史、不下载音视频。晚报继续筛选 agent 开发及产品主题，仅主人可 @ 触发对话。

本地群消息、对话、网页缓存、晚报和投递正文最多保留七天。启动时及每分钟清理；过期对话和群消息查询立即排除。派生回答继承已使用来源的最早到期时间，晚报按窗口起点计算七天期限，因此部分派生内容会提前删除。已有对话缺少来源时间，迁移时保守按本会话最早消息计算到期。停机时无法执行清理，下次启动先清理。QQ、Telegram 和模型服务端副本不由本地清理删除。
